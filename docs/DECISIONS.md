# KEL 결정 기록 (DECISIONS.md)

KEL의 설계 결정을 한곳에 모은다. 세션을 시작할 때 [PROGRESS.md](PROGRESS.md)와 함께
읽고, 결정이 생기거나 바뀌면 갱신한다. 자세한 비교와 근거는 [DESIGN.md](DESIGN.md)에 있다.

상태 표기:

- **확정**: 사용자가 확인함. "(위임)"은 사용자가 결정을 리드 엔지니어(Claude)에게 맡겨
  추천안대로 확정한 것
- **확인 대기**: 추천안을 제시했고 사용자 확인 전. 확인을 받을 수 없는 상태에서 작업이
  필요하면 추천안대로 진행하고, 진행했다는 사실을 이 문서에 적는다.
- **보류**: 뒤 단계에서 정한다. 위임에 따라 그 단계에서 Claude가 정하고 여기에 기록한다
- **대체됨**: 다른 결정으로 바뀜 (어떤 결정으로 바뀌었는지 적는다)

> **2026-10-22 위임 기록**: 사용자가 Phase 0 결정 항목에 대해 "다 너가 정해"라고 답했다.
> 그래서 D-001~D-017을 추천안대로 확정했고, 보류 항목도 해당 단계에서 Claude가 정한다.
> 예외: 공개 배포처럼 되돌리기 어려운 작업은 D-000의 작업 규칙에 따라 실행 직전에 한 번 알리고 확인한다(D-024).

## D-000 프로젝트 헌장 — 확정 (2026-10-22, 사용자 지시)

- 이름: KEL (Kelp Enterprise Linux), os-release `ID=kel`
- 다른 배포판을 베이스로 쓰지 않는 독립 배포판
- 지향: 엔터프라이즈급 안정성 (긴 지원 기간, 보안 업데이트, 서명된 패키지, 재현 가능한 빌드)
- 아키텍처: x86_64, aarch64 (우선순위는 Phase 0에서 정함 → D-001)
- 규모: 1인 개발 + AI, 빌드 팜 없이 가능한 계획
- "바닥부터": 커널, 툴체인, libc 등을 업스트림 소스에서 KEL 자체 빌드 시스템으로 전부 빌드.
  레시피로 언제든 처음부터 다시 빌드 가능. 다른 배포판의 바이너리는 부트스트랩 호스트로만
  쓰고 최종 결과물에는 넣지 않는다.
- 단계: Phase 0 설계 → 1 부트스트랩 → 2 빌드 시스템과 패키지 관리 → 3 첫 부팅 이미지 →
  4 엔터프라이즈 기능 → 5 문서
- 작업 규칙:
  - 세션 시작 때 PROGRESS.md와 DECISIONS.md를 읽고 이어서 작업, 끝날 때 갱신
  - 각 단계는 실제로 돌려서 검증한 뒤 다음으로
  - 패키지 이름, 명령어, 업스트림 동작은 추측하지 말고 문서나 웹에서 확인
  - 업스트림 라이선스를 지키고, 배포하는 바이너리의 소스도 함께 공개되는 구조
  - 서명 개인 키 같은 비밀 정보는 커밋 금지
  - 공개 배포, 외부 푸시처럼 되돌리기 어려운 작업은 먼저 물어보기
  - 큰 결정은 선택지를 정리해 확인받기. 확인받을 수 없으면 추천안으로 진행하고 여기에 기록

## D-001 아키텍처 우선순위와 ISA 기준선 — 확정 (2026-10-22, 사용자 위임)

- **추천**: x86_64를 먼저(Phase 1~3) 하고, aarch64는 같은 레시피의 크로스 빌드로 Phase 2
  후반부터. 기준선 x86-64-v2, ARMv8.0-A. 타깃 triplet은 `x86_64-kel-linux-gnu`, `aarch64-kel-linux-gnu`.
- **근거**: 작업 호스트가 x86_64이고 KVM이 없다. v2는 SLES 16·Amazon Linux 2023과 같고, Proxmox VE의
  새 VM 기본 CPU(`x86-64-v2-AES`)에서 동작한다. v3를 고르면 RHEL 10과 같지만 오래된 CPU와
  보수적인 가상 CPU 모델에서 부팅하지 못한다.
- **대안**: x86-64-v3 기준선, v2 기본 + v3 추가판.
- **영향**: 레시피 형식이 처음부터 크로스 빌드를 지원해야 한다. QEMU 테스트는 CPU 모델을 명시한다.

## D-002 패키지 형식과 매니저 — 확정 (2026-10-22, 사용자 위임)

- **추천**: apk-tools 3과 v3 패키지·색인 형식 채택. 패키지 매니저를 직접 개발하지 않는다.
- **근거**: 의존성이 zlib + OpenSSL(또는 mbedTLS) + 선택적 zstd뿐이라 부트스트랩 초기에 빌드할 수
  있다(호스트에서 4.5초). v3 형식은 Chimera와 OpenWrt 25.12가 운영 중이다. 서명된 색인과 패키지로
  설치·업그레이드·삭제, 신뢰하지 않는 키 거부, 변조 패키지 거부를 직접 확인했고, 서명 전 패키지가
  바이트 단위로 재현됐다([apk PoC](research/2026-10-22-apk-v3-poc.md)).
- **대안**: RPM 6 + tdnf/dnf5 (엔터프라이즈 표준이지만 서명 검증에 Rust가 필요해 부트스트랩이
  무겁다), pacman 7, dpkg + apt 3, 직접 개발.
- **영향**: 패키지 버전 형식 `<버전>-r<리비전>`. KEL이 채울 빈칸: 저장소 신선도 검사, SELinux 라벨
  보정 훅, 롤백(모두 Phase 4 이후), 서명 키 알고리즘(D-019).

## D-003 빌드 시스템 — 확정 (2026-10-22, 사용자 위임)

- **추천**: 자체 빌드 도구 `kel`(D-011) + TOML 레시피(선언적 메타데이터 + 짧은 셸 빌드 단계) +
  bubblewrap 격리(root 불필요, 네트워크 차단, 선언된 빌드 의존성만 든 새 빌드 루트).
- **근거**: 사용자 요구("KEL 자체 빌드 시스템")와 일치한다. 메타데이터를 실행 없이 읽을 수 있어 SBOM과
  CVE 매칭에 바로 쓸 수 있다. 같은 조합(Python + bwrap + apk v3)으로 Chimera cbuild가 독립 배포판을 빌드한다.
  bubblewrap은 이 호스트에서 일반 사용자 권한으로 네트워크를 끊은 채 동작함을 확인했다.
- **대안**: cbuild 포크, melange, abuild, Yocto/Buildroot, Nix/Guix.
- **영향**: Phase 1에서 `tools/kel` 뼈대와 레시피 형식을 확정한다.

## D-004 libc — 확정 (2026-10-22, 사용자 위임)

- **추천**: glibc.
- **근거**: 엔터프라이즈 서드파티 소프트웨어가 사실상 glibc만 지원한다. systemd의 1차 대상이다
  (musl 지원은 v259부터 "불완전"). 업스트림이 release 브랜치에 백포트를 유지한다.
- **대안**: musl 1.2.6.
- **영향**: 포인트 릴리스 tarball이 없으므로 레시피는 release 브랜치 백포트를 패치나 커밋 고정으로 따라간다.

## D-005 컴파일러와 툴체인 — 확정 (2026-10-22, 사용자 위임)

- **추천**: GCC + GNU binutils를 시스템 툴체인으로 쓰고, LLVM/Clang은 필요할 때 일반 패키지로.
  KEL 메이저마다 GCC 메이저 하나를 고정한다. 링커는 ld.bfd.
- **근거**: glibc·커널의 1차 대상이고, GCC 브랜치는 약 3.5년 유지된다. LLVM은 라인마다 수정 기간이
  약 4개월이다.
- **영향**: 현재 기준 버전은 GCC 16.2, binutils 2.47, glibc 2.44. 1.0 동결 때 다시 정한다.

## D-006 init — 확정 (2026-10-22, 사용자 위임)

- **추천**: systemd.
- **근거**: 엔터프라이즈 관리자가 이미 알고, 로그·장치·네트워크·자원 제어·서비스 샌드박스가 통합되어
  있으며, 업스트림이 안정 브랜치 여러 개를 동시에 유지한다.
- **대안**: OpenRC, dinit, s6, runit.
- **영향**: merged `/usr` 필수, 커널 5.10 이상, 빌드에 meson·Python·jinja2 필요. 시간 동기화는 chrony.

## D-007 기본 유저랜드와 파일시스템 배치 — 확정 (2026-10-22, 사용자 위임)

- **추천**: GNU 유저랜드 + util-linux + shadow + Linux-PAM. `/usr` 병합과 `bin`/`sbin` 병합,
  라이브러리는 `/usr/lib` 하나.
- **근거**: 스크립트 호환성. systemd가 split-usr를 지원하지 않고 `bin`/`sbin` 분리 시 taint를 표시한다.
- **대안**: BusyBox/toybox, uutils.

## D-008 부트로더, initramfs, Secure Boot — 확정 (2026-10-22, 사용자 위임)

- **추천**: x86_64·aarch64 모두 UEFI 전용, systemd-boot + 서명된 UKI, initramfs는 dracut-ng.
  Secure Boot는 KEL 자체 키(사용자 등록)로 시작하고 shim 리뷰는 나중에 신청한다. 레거시 BIOS는 지원하지 않는다.
- **근거**: 가장 짧은 부팅 체인이다. shim 리뷰에는 법인 실체, EV 인증서, 보안 연락처 2명,
  FIPS 140-2 Level 2 키 하드웨어가 필요하다. 새 shim은 Microsoft UEFI CA 2023으로만 서명된다.
- **대안**: GRUB 2.14(BIOS 지원), Limine, EFI stub 직접 부팅.

## D-009 설치 프로그램 — 확정 (2026-10-22, 사용자 위임)

- **추천**: Phase 3에서 systemd-sysinstall(systemd 261+)을 먼저 평가한다. 맞지 않으면 systemd-repart,
  bootctl, systemd-firstboot로 작은 `kel install`을 만든다. 무인 설치는 TOML 응답 파일, 클라우드
  이미지는 cloud-init(NoCloud).
- **대안**: Anaconda + kickstart, Calamares, 직접 개발한 TUI 설치기.

## D-010 업데이트 방식 — 확정 (2026-10-22, 사용자 위임)

- **추천**: 패키지 단위 업데이트. 이미지 기반(bootc, systemd-sysupdate 등)은 같은 패키지로 만드는
  변형판으로 Phase 4 이후에 검토한다.
- **근거**: 추가 인프라가 가장 적다. CVE를 패키지 하나씩 처리할 수 있다. 나중 선택지를 막지 않는다.

## D-011 자체 도구 구현 언어 — 확정 (2026-10-22, 사용자 위임)

- **추천**: Python 3.11 이상, 표준 라이브러리만 사용.
- **근거**: systemd(meson, jinja2)와 glibc 빌드에 Python이 어차피 필요하므로 새 부트스트랩 의존성이
  생기지 않는다. KEL 도구의 일은 대부분 조율이고, 무거운 일은 C로 된 기존 도구가 한다.
- **대안**: Go, Rust (패키지 매니저를 직접 만든다면 이쪽이 낫다).

## D-012 커널 정책 — 확정 (2026-10-22, 사용자 위임)

- **추천**: kernel.org 최신 LTS를 추적한다. 업스트림 EOL이 다가오면 같은 메이저 안에서 다음 LTS로
  리베이스한다. kABI는 보장하지 않는다. 개발 기간에는 6.18 LTS를 쓴다(D-021).
- **근거**: 1인이 EOL 이후 커널 백포트를 할 수 없다. 커널 CNA가 CVE를 대량으로 발행하므로
  stable 업데이트 전체를 받는 것이 현실적이다.
- **대안**: LTS 고정 + 직접 백포트, CIP SLTS(6.12, 2035년 중반까지), 메인라인 stable.

## D-013 릴리스 주기, 지원 기간, 버전 체계 — 확정 (2026-10-22, 사용자 위임)

- **추천**: 메이저 3년 주기, 메이저당 5년 지원(일반 3년 + 보안 전용 2년), 일반 지원 중 6개월마다
  포인트 릴리스. 버전은 `major.minor`이고 1.0 전에는 0.x 프리뷰. 지원은 "최선 노력, SLA 없음"으로 명시한다.
- **근거**: 5년은 Ubuntu LTS 표준 지원, RHEL 일반 지원, CRA 최소 지원 기간과 같다. 동시 안정 브랜치를
  2개로 제한할 수 있다.
- **대안**: 2년 주기 + 4년 지원, Alpine식 2년 지원, 10년, 롤링.
- **확정 메모**: 사용자가 판단을 위임했다. 5년은 "최선 노력, SLA 없음" 조건으로 약속하고, Phase 4에서
  보안 업데이트 파이프라인의 실제 처리 시간을 잰 뒤 지원 문서에 반영한다.

## D-014 서명과 신뢰 체인 — 확정 (2026-10-22, 사용자 위임)

- **추천**: 오프라인 루트 키(사용자 보관)가 온라인 저장소 서명 키를 인증하고, 저장소 서명 키가 패키지와
  색인에 서명한다. Phase 1~3에는 세션마다 버리는 개발용 키만 쓴다. 업스트림 소스는 sha256과 지문을
  고정한 서명으로 검증한다.
- **영향**: 키 교체·폐기 절차와 리허설을 Phase 2 완료 조건에 넣는다.

## D-015 빌드 인프라와 산출물 보관 — 확정 (2026-10-22, 사용자 위임)

- **추천**: 개발과 검증은 이 세션에서 하고, 정기적이거나 무거운 빌드와 aarch64 네이티브 빌드는 GitHub
  Actions로 한다(공개 저장소라 x64·arm64 러너 4 vCPU/16 GB 무료, x64는 KVM 사용 가능). 서명은 CI 밖에서 한다.
- **주의**: 공개 저장소의 Actions 아티팩트는 읽기 권한만 있으면 받을 수 있어 사실상 공개 배포다.
  그래서 D-024 정책에 따라 Phase 1~2의 CI는 검사(빌드·테스트)만 하고 바이너리 아티팩트는 올리지 않는다.
- **제약**: 작업당 6시간, 디스크 14 GB, 캐시 10 GB.

## D-016 라이선스와 소스 공개 구조 — 확정 (2026-10-22, 사용자 위임)

- **추천**: 레시피마다 SPDX 라이선스 필수, 라이선스 원문은 `/usr/share/licenses/<패키지>/`에 설치,
  바이너리를 공개할 때 같은 위치에 대응 소스(업스트림 tarball + 패치 + 레시피)를 올린다. 재배포는 되지만
  소스가 없는 펌웨어는 별도 구성요소로 둔다. KEL 자체 코드·레시피·문서는 MIT.
- **대안**: Apache-2.0, 0BSD.

## D-017 보안 기반 — 확정 (2026-10-22, 사용자 위임)

- **추천**: SELinux(refpolicy 기반, targeted 방식, 1.0은 permissive로 시작하는 것도 선택지).
  패키지별 SPDX 3.0.1 SBOM(CISA 2026 최소 요소 포함). 보안 공지는 OSV + Alpine 형식 secdb.
  커널은 LTS stable 업데이트를 전부 받는다. NVD 점수에는 의존하지 않는다.
- **근거**: RHEL과 SLE 16(AppArmor 제거)의 흐름. 기존 취약점 스캐너가 secdb와 OSV를 읽는다.
- **영향**: apk에 SELinux 라벨링이 없으므로 post-commit 훅으로 보완한다(D-002).

## 보류 항목 메모

- **D-018 sudo**: sudo 1.9.17p2는 2025-07 이후 안정판이 없고, sudo-rs 0.2.15는 Rust 툴체인이 필요하다.
  Phase 1~2 최소 시스템에는 필요 없다.
- **D-019 apk 서명 키 (확정)**: PoC에서 RSA-4096 서명은 결정적(두 번 빌드한 결과가 같음)이었고
  ECDSA P-256은 매번 달랐다. 그래서 RSA-4096으로 정했다.
- **D-023 기본 파일시스템**: 아직 조사하지 않았다. Phase 3에서 조사한 뒤 정한다.
- **D-026 기준 문서 (2026-10-22)**: Phase 1을 시작할 때는 LFS 12.4를 기준으로 썼는데, 2026-09-01에
  나온 LFS 13.1(stable)이 우리 버전 세트(binutils 2.47, GCC 16.2.0, glibc 2.44 등)와 같은 버전을 쓴다는
  것을 확인했다. 그래서 기준을 13.1로 옮기고 레시피를 명령 단위로 비교했다. 반영한 차이: GCC pass 2의
  `--disable-fixincludes`·`-nostdinc++`·스레드 모델 지정, libstdc++의 `CXX=$TARGET-gcc`, diffutils의
  캐시 값(`=yes`), glibc 2.44용 autoconf 캐시 값(kel이 `CONFIG_SITE`로 제공), 7장에 zlib과 mpdecimal 추가.
  KEL만의 차이(병합된 sbin, 단일 uid 샌드박스, 버전 없는 문서 디렉터리, 다른 배포판용 최적화 옵션 제거)는 유지한다.
  glibc는 LFS의 수정 패치(2026-08-15 시점) 대신 업스트림 `release/2.44/master`에서 직접 만든 패치를 쓴다.
  그 뒤에 나온 보안 수정(CVE-2026-8674, CVE-2026-18374, CVE-2026-19499 등)이 들어간다.
- **D-027 버전 선택 (2026-10-22)**: LFS가 고른 버전이 아니라 검증 가능한 최신 안정판을 쓴다(보안 수정이
  가장 많이 들어간 상태). 예외: 업스트림이 직접 "UNTESTED"라고 표시한 bc 7.1.0 대신 7.0.3(production),
  OpenSSL은 D-020대로 3.5 LTS(3.5.9). 서명이 없는 소스(libffi, lz4, pkgconf, iana-etc, Python 패키지 등)는
  sha256 고정과 공식 체크섬 대조로 받아들이고, 레시피 주석에 확인 방법을 적는다.
- **D-024 공개 배포 (정책 확정)**: 되돌리기 어려운 작업이므로, 정책은 정해 두되 실제로 처음 공개하기
  직전에는 사용자에게 한 번 확인한다(D-000 작업 규칙).
